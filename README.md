### Домены маркетплейса
- Users: аккаунт пользователя, роль (покупатель или продавец), аутентификация
- Catalog: список товаров, инфрмация о товарах, карточки товаров
- Publication: публикация товаров продавцом
- Personalization: персонализированный каталог пользователя, клики, часто просматриваемые товары
- Orders: заказы пользователя, статусы заказов, адреса доставки
- Payments: платежы заказов, статусы платежей
- Notifications: пользовательские уведомления о статусах заказа

### Разбиение доменов по сервисам
- User Service:
  - домен Users
  - отвечает за аккаунт пользователя и аутентификацию
  - владеет данными о пользователях
- Catalog Service:
  - домены Publication, Catalog
  - отвечает за публикацию товаров продавцом, каталог товаров, карточки товаров
  - владеет данными о товарах
- Personalization Service:
  - домен Personalization
  - отвечает за персонализированную ленту пользователя
  - владеет данными о кликах, просматриваемых товарах пользователя
- Order Service:
  - домен Orders
  - отвечает за список заказов как для покупателя, так и для продавца
  - владеет данными о заказах
- Notifications Service:
  - домен Notifications
  - отвечает за уведомления пользователям
  - владеет данными об уведомлениях
- Payment Service:
  - домен Payments
  - отвечает за оплату заказа, статусы платежей
  - владеет данными о статусах платежей
 
### Взаимодействие между сервисами
Синхронное взаимодействие:
- Order Service отправляет информацию об оплате товара в Payment Service
  
Асинхронное взаимодействие:
- Personalization Service получает обновления о товарах из Catalog Service
- Order Service через броккер отправляет информацию об уведомлениях в Notifications Service

### Альтернативные варианты декомпозиции
**Вариант 1**
Для каждого домена отдельный сервис. Тогда вместо общего Catalog Service будут Catalog Service и Publication Service.
Плюсы: четкое разделение ответственности
Минусы: лишние взаимодействие между Catalog Service и Publication Service (высокий coupling), а также общая база данных 

**Вариант 2**
Один общий сервис для управления каталогом товаров, который видит пользователь. Тогда вместо Personalization Service и Catalog Service будет один общий Catalog Service для доменов Personalization, Publication и Catalog.
Плюсы: один большой сервис легче дшля восприятия, чем много маленьких
Минусы: Плохое разделение ответственности, одна большая база данных, слишком мало связей между доменами Personalization и Publication (низкий cohesion)

**Итог:** Выбранная архитектура обладает оптимальным соотношением coupling и cohesion (низкий coupling и высокий cohesion).
